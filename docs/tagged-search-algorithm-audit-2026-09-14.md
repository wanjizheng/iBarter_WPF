# TAG 搜索算法审计：十分钟未找到改进的原因

> 本文记录修复前的诊断与反例。后续生产实现和验证见 [普通／TAG 搜索修正与验收](tagged-voyage-search-2026-09-14.md)，不要将下文的旧队列策略视为当前主搜索。

## 结论

当前 TAG 搜索存在明显的搜索质量问题。未找到改进不能解释为用户数据无法使用 TAG，更不能解释为单船方案已经最短。此前运行满十分钟、完整回放通过，验证的是运行时长和已返回方案的合法性，没有验证搜索是否能发现已知可行的改进。

本次只增加可选诊断计数和独立反例工具，未更换生产搜索策略，也未覆盖用户的运行目录存档。

## 真实数据反例

输入为用户的 27 项交换，使用原有码头开关、仓库库存、人物和小象参数。双方都从伊利亚装货开始；不把删除默认 Velia→Iliya 航段算成 TAG 收益。

| 项目 | 上次十分钟搜索的单船结果 | 完整验证的 TAG 反例 |
| --- | ---: | ---: |
| 路线数 | 4 | 3 |
| 总航行距离 | 183,419.554 m | 183,377.068 m |
| 完成的交换项目 | 27 | 27 |
| 最大航行载重 | 24,411 LT | 24,411 LT |
| 船的正常载重上限 | 25,100 LT | 25,100 LT |

距离只缩短 **42.487 m**，不能包装成大幅航行收益；但它已经是“合法、更短、路线更少、实际使用 TAG”的明确反例。

反例保留前两条路线，合并第三、第四条路线：

1. 第三条路线出发前，在伊利亚切小号，通过小象仓库叠货，将第四条路线需要的「八角纹样保管箱」5 个（共 5,000 LT）放到小号身上，切回主号。
2. 按原第三条路线完成阿利赫恣、哈科班等交换，到达并完成 Sausan 的交换。
3. 把原来的 Sausan→Iliya→Dallae 改为 Sausan→Lema→Dallae。
4. 在 Lema 码头，先把船上的「石尾红萝卜健康餐箱子」2 个转到主号，释放 4,000 LT；切小号，把预装的 5 个保管箱转到船上，再将另外 2 个健康餐箱子从船转到小号。主号、小号各自最终携带 4,000 LT 货物及原有 800 LT 占用。
5. 切回主号，继续 Dallae、Epheria 的交换，在 Epheria 卸下船、主号和小号上的货物。

每一步都经过原有 `TaggedTransportSimulator.TryApply`；最终再经过 `Verify` 完整回放。没有启用新的码头、增加角色容量、修改交换数量或虚构库存，所有航行均未超过船的正常载重。最终货物落到 Epheria 仓库，位置变化包含在候选库存快照中。这是当前软件规则下的验证，不是新的 EU 游戏实测。

更关键的是：反例后半段 **34/34 个操作都已由当前 `Actions` 生成器提供**。这个反例的失败点不是缺少某个操作类型，而是搜索没能将这些合法操作组合成完整方案。

## 确认的问题

### 1. 预装没有得到任何搜索优先级

`Routing/TaggedTransportPlanner.cs` 的 `Score` 在交换未全部完成时，主要使用：

`已航行距离 + 权重 × 剩余交换比例`

装货、切号、召唤小象、通过小象把货装到小号身上，都不改变这两个量。实际反例的连续五个准备动作，前后六个评分全部为 **234,765.788**。评分没有判断这些货物能否在后续码头上船、是否能合并下一航次、是否避免一次回仓。

评分相同的候选依靠入队顺序排列。大量没有明确后续用途的库存排列、转移和切号，与已经完成有效预装的状态处于同一层级；有限队列无法可靠保留后者。低评分本身也不是剩余航行距离的严格下界，不能据此宣称全局最优。

### 2. 自定义时长主要增加重启轮次，没有延续被截断的搜索

主界面时长确实传入了。但每轮重新创建 `seen` 和队列；x86 下 `seen` 达到 15,000 条就终止该轮。达到上限的是生成并登记的状态数量，并非已充分探索的完整候选数量。轮次变化调整权重、分支顺序和单船结果的前缀，仍没有直接的航次合并搜索。

同一真实输入、x86、30 秒诊断窗口记录如下（诊断哈希开销会影响吞吐量，不能作为纯性能基准）：

| 指标 | 数量 |
| --- | ---: |
| 搜索轮次 | 31 |
| 达到状态上限的轮次 | 30 |
| 展开次数 | 141,954 |
| 不同的货物／角色／剩余任务状态 | 36,628 |
| 展开时小号带货 | 74,288 |
| 展开时小象带货 | 73,435 |
| 完整候选 | 48 |
| 优于单船基线的候选 | 0 |

约 **74.2%** 的展开重复访问相同的货物／角色／任务状态。不同历史路径可能合理地到达同一状态，因此不能把这些访问全部等同于无用计算；但该结果结合 30 次状态上限重启，证明“展开数很大”不能当作有效搜索覆盖率。它也证明 TAG 分支确实在运行，而非开关完全没进入 TAG 算法。

### 3. 队列裁剪与状态登记不匹配

候选在入队前就写入 `seen`；x86 队列超过 2,500 个时，只留下 1,250 个，其余候选被丢弃，但对应 `seen` 项仍在。后续达到相同状态、距离／步骤数不更好的路径，也会被挡掉，即使原候选从未展开。

30 秒诊断发生 231 次队列裁剪，丢弃 291,261 个排队状态。这是有限搜索质量和覆盖率的问题；不能仅靠延长墙钟时长修复。

### 4. 最终目标与中途去重目标不一致

`TaggedDistanceObjective.Compare` 最终按“距离、路线数、操作数”比较；搜索中 `seen` 却只比较 `(Distance, Steps)`，状态键也不包含路线分段所需的历史阶段。同一物理库存状态、同距离下，操作更少但回仓更多的历史可能压掉最终目标更偏好的历史。

这是路线数次级目标的缺陷，不能把它单独当作本次 42.487 m 距离反例的已证实成因。

### 5. 原来成熟的路线级优化没有扩展到 TAG

`TaggedShipRouteBaseline.Build` 调用普通规划器时，使用 Balanced，时间最多 5 秒，然后完整重放得到单船保底。主界面 Custom／Extreme 接下来进入的是 TAG 的逐操作状态队列，并未把原来的路线级合并、重排等优化扩展为支持独立人物库存的版本。

因此，“搜索模式和时长接通”与“原来的搜索算法已经完整支持 TAG”是两回事。上次修复完成了前者，没有完成后者。

## 修正应采用的结构

应把搜索重点提高到完整航次及合法补货方案，而不是主要排列单次搬货动作：

1. 保留经过回放验证的普通路线作为 incumbent。
2. 显式生成相邻／相关航次合并、交换岛插入和重排、回仓点替换等候选。
3. 为候选计算出发预装清单、主号／小号／小象的具体分配，以及每个可用码头的腾空间和补货次序。
4. 将“切号→召唤→叠货→装到人物→切回”作为可解释的准备方案生成，但最终仍展开成原来的逐步动作，逐步验证真实货物位置、接收限制和船重。
5. 对有希望的完整方案持续做局部改进，保持搜索覆盖信息；裁剪与去重一致，状态比较与最终距离／路线数目标一致。
6. 验收必须包括本次三路线反例和能明确证明 TAG 收益的不同库存／港口场景。运行满时间、出现 TAG 操作、回放合法分别验证不同性质，不能互相替代。

## 复现和交付范围

`Tools/TaggedTransportUiSmoke` 增加两个独立入口：

- `--audit-algorithm <存档路径>`：构造并逐步验证这个真实数据反例，检查当前动作生成器是否覆盖每个操作，并输出准备过程的评分。
- `--trace-search <存档路径>`：对当前算法执行 30 秒可选诊断，输出跨轮次状态指纹去重后的计数。

输出保存在工具自身目录的 `tagged-audit-counterexample.json` 和 `tagged-search-diagnostics.json`。用户实际存档只读，SHA-256 保持 `9A8FAB39BFCB847C37AAB5522C8D0E0F49E87760513D545B0AF3AF79BA97B688`。

构建通过；新增可选诊断后原 TAG 集成测试 5/5 通过。生产候选生成、评分、剪枝和预算策略未在此次审计中改写，后续实现不能把本报告当作搜索质量已经修复的验收。
