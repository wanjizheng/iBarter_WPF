# 自动路线精修设计

## 目标

在现有“Planner 自动规划 → 船舱多路线 → 地图虚线”链路上补齐真实航行所需的信息和约束：多仓库装卸、中文图标步骤、自动持久化、启动时船舶属性加载、特殊海峡航行距离，以及跨路线重建优化。

## 已确认的产品规则

- `ALL` 只用于同时展示所有路线；船舱步骤与载重仍保留最后一次选择的具体路线。
- 装货、卸货与交换都是同一条路线中的正式步骤。经过仓库但没有物品操作时不显示仓库步骤。
- 输出物品优先卸到规划开始时已经保存该物品的仓库；若多个仓库都有，则由总航程决定访问顺序。
- Crow Coin 不生成卸货步骤。其他有重量、但所有仓库初始数量均为零的输出物品，卸到离当前航线最近的仓库。
- 一条路线允许在多个仓库分段装货、分段卸货；每个步骤只列出本次实际变化的物品。
- `InitialLT`、任意中间步骤的 `CurrentLT` 与 `ExtraLT` 之和，以及峰值均不得超过 `TotalLT`。
- 自动路线生成成功后立即保存。下次启动仅在 Planner、仓库、船舶容量和坐标配置指纹一致且回放验证通过时恢复；否则安全地忽略旧计划。
- 船舶属性在应用启动时读取，不再依赖手动点击 Planner 的“加载”。

## 航行几何

普通海域仍用直线距离。特殊区域使用本地小型航行走廊图计算真实航行距离，但地图虚线只负责清晰展示访问顺序，始终在相邻停靠岛之间画直线：

- 右上区域节点：`Halmad`、`Kashuma`、`Derko`、`Hakoven`、`Arehaza`。
- `Halmad` 是右上区域进出外部海域的双向唯一门户。外部到任何右上岛必须先到 Halmad；右上岛到外部必须先返回 Halmad。
- Halmad 可作为纯导航途经点，不要求存在交换或仓库操作。
- 南部 `Grandiha` 与 `Midnight` 使用确认过的南部走廊折线。
- 航行走廊的中间导航点不显示在地图上，避免密集短线段重置虚线节奏后看起来像实线。
- 计算路径和显示路径职责分离：前者服务于路线成本，后者只连接实际停靠岛。

Velia 的航行坐标调整到码头附近；地图展示点按用户在控件中确认的约 `Margin="464,411,326,29"` 保留为显示坐标，展示坐标与航行坐标继续分离。

## 路线优化

现有单路线内部 relocate/swap/2-opt 保留，并增加“成对破坏—重建”：

1. 选择两条路线并合并其交换任务。
2. 从两条路线之前的真实仓库库存状态开始，以容量、库存、交换依赖和仓库访问为硬约束重建。
3. 接受路线数更少的方案；路线数相同时只接受总走廊距离、装货停靠数、峰值载重按字典序更优的方案。
4. 将后续路线完整回放；只有整份计划仍通过验证才提交替换。
5. 受 `MaxLocalMoves` 和确定性排序限制，保证大规模规划不会无界运行。

这一优化允许把原先被贪心拆开的相邻岛屿重新组合，例如容量允许时把右上五个交换点合并成一次进入 Halmad 门户后的完整访问。

## UI 与本地化

- 仓库步骤标题使用本地化仓库名，不直接显示 `Velia`、`Iliya` 等内部 ID。
- 每个装货/卸货物品显示图标、当前语言物品名和数量，不再显示 ItemID。
- 装货/卸货物品按纵向单列显示，每个物品独占一行，窄船舱中不得横向截断。
- 交换步骤维持现有图标形式。
- ALL 模式中每条路线使用不同颜色/虚线样式；选中单路线时船舱载重和步骤同步切换。

## 安全与兼容

- 手动船舱排序和手动金色虚线路线保持原样。
- 持久化采用带 schema/configuration version 的独立 JSON，不覆盖 Planner、StorageManager 或手动船舱数据。
- 旧计划读取失败、版本不一致或验证失败时不影响应用启动。
- 算法层继续保持纯 C#，以独立测试项目覆盖，不依赖 WPF UI 测试。
